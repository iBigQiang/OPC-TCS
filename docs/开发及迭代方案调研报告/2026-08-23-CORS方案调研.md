# CORS 方案调研：能否改 feedgrab-x 去掉 Pages Function

**日期**：2026-08-23
**结论**：技术可行，但**不建议**。中转层应当保留。
**状态**：调研结论，本轮不改代码

---

## 1. 问题来源

当前「在线抓取」的请求链路是：

```
浏览器 → POST /api/importer（Cloudflare Pages Function，同源）
       → POST https://importer-x.hitu.me/import/twitter
```

中转层存在的直接原因是实测发现：

```
OPTIONS https://importer-x.hitu.me/import/twitter
→ 405 Method Not Allowed，且响应中没有任何 Access-Control-Allow-* 头
```

浏览器发带 `Authorization` 头的跨源 POST 前必须先过预检，预检失败请求就被拦下。

提出的探索方向：**优化 feedgrab-x 并重新部署，让它自己发 CORS 头，从而去掉 Function。**

## 2. 技术可行性：完全可行，约 5 行代码

`docs/feedgrab-x/app/main.py` 是标准 FastAPI 应用（`from fastapi import FastAPI`），当前**没有任何 CORS 中间件**（全目录 grep `CORS` / `allow_origins` / `Access-Control` 均无命中）。

加上即可：

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://tcs.opc.tools"],
    allow_methods=["POST", "OPTIONS"],
    allow_headers=["authorization", "content-type"],
)
```

FastAPI 的 `CORSMiddleware` 会自动处理 `OPTIONS` 预检并回 204 + 正确的头。改完重新 build Docker 镜像、重启容器即可生效。

**所以「能不能做到」的答案是：能，很容易。**

## 3. 为什么仍然不建议

理由都在安全模型，不在技术难度。

### 3.1 令牌会从「同源收敛」退化为「公网直发」

当前架构下，`IMPORT_SERVICE_TOKEN` 存在访客浏览器的 `localStorage`，通过**同源请求**发给 `/api/importer`。同源意味着：只有本站页面能读到它、只有本站能收到它。

改成直连后，浏览器必须把令牌**直接发往 `importer-x.hitu.me` 这个第三方源**。令牌暴露面从「本站」扩大到「本站 + 目标服务 + 中间任何能观察跨源请求的东西」（浏览器扩展、企业代理、调试工具）。

### 3.2 `allow_origins` 是个容易写错的开关

一旦为了图省事写成 `allow_origins=["*"]`（这在实践中极常见），**任何网站的 JS 都能调用你的抓取服务**——只要它以某种方式拿到了令牌。而 CORS 的 `*` 配合 `Authorization` 头本身还有额外的规范限制，配错时的排查成本很高。

写死具体域名虽然安全，但每加一个部署环境（预览分支、自定义域、本地开发的 `127.0.0.1:8798` 与 `:8799`）都要改服务端白名单并重启容器。

### 3.3 会丢掉 SSRF 防护这一层

Function 目前不只是转发，它还做了一件事：**校验上游地址**。因为前端设置里允许改「接口地址」，如果没有白名单，这个端点就是一个开放代理——任何人都能让 Cloudflare 的服务器去请求任意地址（包括内网）。

直连方案下这层校验没有了。前端直接决定请求谁，等于把校验交给了攻击者。

### 3.4 不发 CORS 头是设计意图，不是缺陷

接口文档 `importer-x-api.md` 第 11 行原文：

> 该服务运行在小主机 Docker 中，通过 Cloudflare Tunnel 暴露给公网。网站后台只通过服务端调用它，**前端页面不直接持有 token**。

服务从一开始就是按「只被服务端调用」设计的。补 CORS 头等于把一个内部服务改成面向浏览器的公开 API，这是产品定位的改变，不是修 bug。

## 4. 中转层的额外价值

即便 CORS 问题被解决，Function 依然值得保留，因为它已经/可以承担：

| 能力 | 当前 | 说明 |
|---|---|---|
| 绕开 CORS | ✅ | 直接动因 |
| 令牌收敛在同源 | ✅ | 见 3.1 |
| SSRF 白名单 | ✅ | 见 3.3 |
| 管理入库密码校验 | ✅ | 密码存 Cloudflare 环境变量，前端拿不到正确值 |
| 限流 / 配额 | 未做 | 有中转层才有地方做 |
| 审计日志 | 未做 | 同上 |
| 上游地址切换 | ✅ | 换抓取服务不用改前端 |

去掉它省下的是一个约 80 行的文件，失去的是上述所有挂载点。

## 5. 如果仍然想改 feedgrab-x，建议改什么

不是加全量 CORS，而是这两件事之一：

1. **给 `/health` 加 CORS**（只读、无鉴权），方便前端做服务探活并给出「抓取服务离线」的友好提示，不涉及令牌。
2. **把 `OPTIONS` 从 405 改成 204**，即便不打算支持浏览器直连，也让预检失败的错误信息更清晰——现在的 405 会让人误以为端点不存在。

这两项都不影响本项目当前架构，属于纯增益。

## 6. 结论

| 问题 | 答案 |
|---|---|
| 能通过改 feedgrab-x 解决 CORS 吗 | 能，FastAPI 加 `CORSMiddleware`，约 5 行 |
| 应该这么做以去掉 Function 吗 | **不应该** |
| 理由 | 令牌暴露面扩大、白名单易配错、丢失 SSRF 防护与密码校验挂载点、违背服务原本的设计意图 |
| 建议 | 保留 Function 中转层；如要改 feedgrab-x，只给 `/health` 加 CORS 或把 `OPTIONS` 改成 204 |

# 背景图库扩容 + 网格改造方案

**日期**：2026-08-24
**范围**：背景库从 34 项扩到 152 项，全部按 `bj_n-` 编号；缩略图加名称浮动条；网格改为折叠展开 + 关键词搜索。

---

## 一、背景与目标

当前背景库 34 项（24 张 1080×1440 照片 + 10 个渐变 SVG）。三个问题：

1. `manifest.json` 里早就有中文名，但界面上只做了 `title` 悬浮提示，**看不见**。
2. 缩略图一次性全部铺出，图库一扩就会把右栏拉得很长。
3. 没有检索手段，图一多就找不到。

参考站 `dontbesilent-tweet-card-studio.vercel.app` 这三件事都有。本轮对齐它的交互，并把它的 118 张图库纳入本项目。

同时把首张背景（页面默认背景）换成强哥自己的照片。

## 二、参考站实现（读源码所得，非猜测）

从 `_next/static/chunks/page-kIcdsr1l.js` 解出它的图库定义：

```js
var X = [
  {id:'misty', name:'雾谷晨光', src:'/backgrounds/misty-valley.jpeg', keywords:'山谷 自然 清晨 雾'},
  ... 共 8 条具名 ...
  ...Array.from({length:110}, (e,t) => {
    let n = String(t+1).padStart(3,'0');
    return {id:`travel-${n}`, name:`旅行素材 ${n}`, src:`/backgrounds/travel-${n}.jpeg`,
            keywords:'旅行 城市 山海 雪景 汽车 风景 建筑'};
  })
];
```

8 + 110 = **118 张**，与强哥观察一致。**那 110 张的名称与关键词是程序批量生成的**，源站自己也没逐张起名。

UI 结构（`.background-section`）：搜索框 → `当前显示 N / M 张` → `.background-grid`（4 列）→ 「查看更多背景」→ 上传 → URL 输入。常量 `ut = 16`：首屏 16 张、每次 +16。搜索时重置回 16。

关键 CSS：

```css
.background-grid button { aspect-ratio:1; position:relative; overflow:hidden; border-radius:8px }
.background-grid img    { object-fit:cover; width:100%; height:100%; display:block }
.background-grid span   { color:#fff; text-align:center; background:#0000009e;
                          padding:5px 3px; font-size:9px; position:absolute; inset:auto 0 0 }
```

底部名称条就是 `button > span` 的绝对定位。`<img>` 带 `loading="lazy" decoding="async"`。

## 三、实测数据

全部 118 张在内存中跑完压缩，**不是估算**：

| 参数 | 总体积 | 平均 | 最大 |
|---|---|---|---|
| 原始 | 21.9 MB | 185 KB | 909 KB |
| 1080 宽 / ≤200 KB | **17.9 MB** | 155 KB | 216 KB |
| 1080 宽 / ≤140 KB | 15.3 MB | 132 KB | 216 KB |
| 960 宽 / ≤120 KB | 14.2 MB | 123 KB | 216 KB |

**更正一个错误估计**：规划时口头估「压缩后 8–12 MB」，实测是 17.9 MB。原因是源图本身已压得紧（平均 185 KB @ 960×1280），重编码只省得下 4 MB。要压到 10 MB 得牺牲尺寸到 720 宽，导出会明显模糊，不做。

两个必须落进代码的实测结论：

1. **`photo-snow-peaks.jpg`（413 KB, 1080×1440）重编码 q82 反而涨到 446 KB。** 压缩函数必须「产物 ≥ 原图就退回原图」，否则批量处理会让一部分图变大。
2. **源站图多为 960×1280**，用于 `tall`(1080×1920) 导出要放大 1.5 倍。背景会被压暗 10% 且大部分被卡片遮住，可接受；但这批图不是为 9:16 准备的，别指望它在 9:16 下锐利。

工具：Pillow 10.4.0（本机无 ImageMagick）。

## 四、已确认决策

| 项 | 决定 | 备注 |
|---|---|---|
| 110 张 travel 的中文名 | 沿用源站批量名「旅行素材 NNN」 | 逐张看图起名成本高，本轮不做 |
| 体积 | 1080 宽上限 + 质量自适应至 ≤200 KB | 实测总 17.9 MB |
| 旧分享链接 | 直接重命名 | 但见下方「顺手兜底」 |
| 网格节奏 | 首屏 5 列 × 8 行 = 40 张，每次 +20（4 行） | 152 张需点 6 次全展开 |

## 五、命名与编号

文件名 `bj_<n>-<slug>.<ext>`，显示名 `<中文名> <3 位 n>`。

**序号一次性固定、写死在清单里**，不按列表位置自动计算——否则以后往中间插一张图，后面所有文件都得重命名。

| 区段 | 数量 | 内容 | 示例 |
|---|---|---|---|
| `bj_1` | 1 | 强哥照片（默认背景） | `bj_1-ibigqiang.jpg` /「人物竖屏 001」 |
| `bj_2`–`bj_24` | 23 | 现有照片（去掉 wuyanzu） | `bj_24-cafe-silhouette.jpg` /「街角咖啡馆 024」 |
| `bj_25`–`bj_32` | 8 | 源站具名图 | `bj_25-misty-valley.jpg` /「雾谷晨光 025」 |
| `bj_33`–`bj_142` | 110 | 源站 travel-001…110 | `bj_33-travel-001.jpg` /「旅行素材 033」 |
| `bj_143`–`bj_152` | 10 | 渐变 SVG | `bj_143-ink-dawn.svg` /「墨色黎明 143」 |

共 **152 项**。

细节：

- `photo-ibigqiang.png` 2.59 MB PNG → 转 JPG（1152×2048 缩到 1080×1920，q86）。照片无透明需求，与项目既有约定（头像用 JPG 不用 PNG）一致。
- 渐变 SVG 也纳入编号，`gen_backgrounds.py` 改文件名模板一行即可，保持命名体系统一。
- 扩展名统一 `.jpg`（重编码后由我们决定，不保留源站的 `.jpeg`）。
- 现有 23 张照片**不重编码**（已是 1080×1440、平均 203 KB，重编码只会变大），只 `git mv` 改名。

⚠️ **`.gitignore:24` 有 `bg_*.jpg`**（无斜杠 = 匹配任意层级）。前缀是 `bj_` 不是 `bg_`，已用 `git check-ignore` 实测确认不被忽略。**一字之差会让全部图片被 git 静默忽略、部署后全部 404。**

## 六、manifest 结构变更

加 `keywords` 字段供搜索：

```json
{ "file": "bj_1-ibigqiang.jpg", "name": "人物竖屏 001", "keywords": "人物 竖屏 写真" }
```

- 现有 23 张 + 8 张具名 + 10 渐变：逐条手写关键词（41 条，一次性）。
- 110 张 travel：写 `旅行 素材`，**不照搬**源站那串 `旅行 城市 山海 雪景 汽车 风景 建筑`——照搬会让搜「城市」命中全部 110 张，把真正叫「城市屋顶」的淹掉。

## 七、前端改造要点

### 两个必须先拆的耦合

1. **`renderBackgroundGrid()` 兼着设默认背景的副作用**（`app.js:593` 的 `i === 0 && !state.bg`）。改造后网格会因搜索/展开被反复重渲染，这个副作用会重置用户的选择。→ 移到 `init()` 里 manifest 加载后执行一次。
2. **`setBg()` 靠传入的 DOM 元素打 `active`**（`app.js:597-602`）。重渲染后元素被销毁，选中态就丢了。→ 改为由 `state.bg` 驱动，渲染时比对 src。

### 新增状态与函数

- state：`bgQuery: ""`、`bgVisible: 40`、`customBgs: []`；常量 `BG_INITIAL = 40` / `BG_PAGE = 20`。
- `filteredBackgrounds()`：按 `bgQuery` 匹配 `name` + `keywords`。
- `renderBackgroundGrid()`：清空 → 先渲染 `customBgs`（不参与搜索与折叠计数）→ 渲染过滤结果前 `bgVisible` 张 → 更新计数 → 有剩余则显示「查看更多背景」。缩略图补 `<span class="bg-name">` 与 `loading="lazy" decoding="async"`。
- 搜索 input：`bgQuery = v; bgVisible = BG_INITIAL; render()`（与源站一致，搜索重置折叠）。
- `addCustomThumb()`：改为 push 进 `state.customBgs` + 重渲染。现在的直接 append 一次重渲染就没了。

### 顺手兜底：一行救回旧链接

`resolveBgParam()`（`app.js:1402`）加一条宽松匹配——参数值与 `b.file` 都剥掉 `^(photo-|bj_\d+-)` 前缀再比。旧链接 `?bg=photo-forest-path` 即可命中 `bj_11-forest-path.jpg`。

决策时选的是「不管旧链接」，理由是不想维护 23 条映射表；但一行正则就能覆盖，成本比映射表低得多，所以做掉。

### 样式

- `.bg-thumb` 加 `position: relative`；新增 `.bg-name` 底部浮动条，参考站的 9px 按项目字号体系调到 `.58rem` 并加单行截断。
- 保持我们的 `aspect-ratio: 3/4`（贴合卡片比例），不跟参考站的 1:1。
- 搜索框沿用 `#bg-url` 的圆角风格；「查看更多」沿用 `ghost-btn` 盒模型——上一轮刚把预览顶栏六个按钮统一成 28.8px 等高，别引入第七种高度。
